## Overview

duck-iam provides client libraries for checking permissions in the browser. The recommended
pattern is server-driven: generate a `PermissionMap` on the server, send it to the client,
and use it for all UI decisions.

<Callout type="warning" title="A client-side check hides UI. It is not authorization.">
The permission map is a snapshot of decisions a server already made, serialised over the wire
and held in a browser the user controls. Every value in it can be edited from a devtools
console, and nothing on the client re-derives it. `can()` decides what to render; the request
the button fires must be authorized again on the server, by the engine, against the live
policy set. None of these libraries contains an evaluator -- see the server middleware for
the check that actually decides.
</Callout>

Every client library supports the same core operations:

- `can(action, resource, resourceId?, scope?)` -- returns `true` if the permission is granted
- `cannot(action, resource, resourceId?, scope?)` -- returns `true` if the permission is denied
- `allowedActions(resource)` -- the actions the map allows on that resource type
- `hasAnyOn(resource)` -- whether the map allows anything on that resource type

Client-side checks are synchronous lookups against the pre-computed permission map. No network requests happen during these checks.

### The PermissionMap

A `PermissionMap` is a flat object where keys encode the permission and values are booleans.
Keys follow one of four formats depending on which fields are present:

```typescript
{
  // Format: "action:resource"
  "create:post": true,
  "delete:post": true,
  "manage:team": false,

  // Format: "action:resource:resourceId"
  "delete:post:abc123": false,

  // Format: "@scope:action:resource" - the @ marks a scope
  "@org-1:manage:billing": true,

  // Format: "@scope:action:resource:resourceId"
  "@org-1:update:post:post-42": true,
}
```

Generate it on the server using `engine.permissions()` or the `getIamPermissions` helper from `@gentleduck/iam/server/next`. When a key is not found in the map, all client libraries return `false` (deny by default).

Values have to be the literal boolean `true`. Nothing validates the map -- it arrives as
`JSON.parse` output and the type is erased -- so `can()`, `allowedActions()` and `hasAnyOn()`
all test `=== true` rather than truthiness. A server that emits `"read:post": "false"` grants
nothing, which is the safe reading of a string that is truthy in JavaScript.

The map is also stale by construction: it was computed once. A role revoked after the map was
built stays visible in the UI until something reloads it.

### Permission keys and iamBuildPermissionKey

All client integrations use the same internal key builder:

```typescript
import { iamBuildPermissionKey } from '@gentleduck/iam'

iamBuildPermissionKey('delete', 'post')
// "delete:post"

iamBuildPermissionKey('update', 'post', 'post-42', 'org-1')
// "@org-1:update:post:post-42"  -- the `@` marks the leading segment as a scope
```

Inside a segment, `:` and `\` are backslash-escaped and a leading `@` is escaped, so a resource
literally named `a:b` keys as `read:a\:b`. That is why a map must never be introspected with
`key.split(':')`: the shipped helpers parse through the same builder and reject any key
outside its image, and a hand-rolled split disagrees with `can()` on the same map.

You rarely need to call `iamBuildPermissionKey()` directly -- the React, Vue, and vanilla clients call it internally. It is useful when generating or inspecting `PermissionMap` objects in tests, server endpoints, or custom client helpers.

## React

```
import { createIamAccessControl, createIamPermissionChecker } from '@gentleduck/iam/client/react'
```

### Setup

Create the access control system once at app initialization. Pass your React import to avoid a hard dependency.

```typescript
// lib/access.tsx
import React from 'react'
import { createIamAccessControl } from '@gentleduck/iam/client/react'

export const {
  AccessProvider,
  useAccess,
  usePermissions,
  Can,
  Cannot,
} = createIamAccessControl(React)
```

### AccessProvider

Wrap your app (or a subtree) with the provider. Pass the permission map generated on the server.

```tsx
// app/layout.tsx (Next.js example)
import { AccessProvider } from '@/lib/access'
import { getIamPermissions } from '@gentleduck/iam/server/next'

export default async function RootLayout({ children }) {
  const session = await auth()
  const permissions = session?.user
    ? await getIamPermissions(engine, session.user.id, [
        { action: 'create', resource: 'post' },
        { action: 'delete', resource: 'post' },
        { action: 'manage', resource: 'team' },
        { action: 'read', resource: 'analytics' },
      ])
    : {}

  return (
    <AccessProvider permissions={permissions}>
      {children}
    </AccessProvider>
  )
}
```

### useAccess hook

Read permissions from context in any component.

```tsx
import { useAccess } from '@/lib/access'

function PostActions({ postId }: { postId: string }) {
  const { can, cannot } = useAccess()

  return (
    <div>
      {can('update', 'post') && <button>Edit</button>}
      {can('delete', 'post') && <button>Delete</button>}
      {cannot('manage', 'team') && <span>Contact an admin to manage teams</span>}
    </div>
  )
}
```

The hook returns:

| Property | Type | Description |
| --- | --- | --- |
| `permissions` | `PermissionMap` | The raw permission map |
| `can` | `(action, resource, resourceId?, scope?) -> boolean` | Check if a permission is granted |
| `cannot` | `(action, resource, resourceId?, scope?) -> boolean` | Check if a permission is denied |
| `allowedActions` | `(resource) -> string[]` | Actions the map allows on that resource type |
| `hasAnyOn` | `(resource) -> boolean` | Whether the map allows anything on that resource type |

`allowedActions` returns `string[]`, not your action union: re-asserting the union over keys
parsed from unvalidated JSON would hide a malformed map instead of surfacing it. Narrow with
your own predicate if you need the union back.

`AccessProvider` copies the map into a snapshot and answers every check from the copy, so
mutating the object you passed changes nothing and re-renders nothing. Pass a new object when
the grants change.

Called outside a provider, every member of the context is a gate rather than a permissive
stub. Under `NODE_ENV=development` all five throw; anywhere else -- including a browser bundle
where `process` was never shimmed -- `can` answers `false`, `cannot` `true`, `allowedActions`
`[]` and `hasAnyOn` `false`. A silent deny for a missing provider looks exactly like a
correctly configured user with no permissions, which is why development throws instead.

### Can and Cannot components

Declarative permission gates for JSX.

```tsx
import { Can, Cannot } from '@/lib/access'

function Dashboard() {
  return (
    <div>
      <Can action="read" resource="analytics">
        <AnalyticsPanel />
      </Can>

      <Can action="manage" resource="team" fallback={<UpgradePrompt />}>
        <TeamSettings />
      </Can>

      <Cannot action="create" resource="post">
        <p>You do not have permission to create posts.</p>
      </Cannot>
    </div>
  )
}
```

`Can` props:

| Prop | Type | Required | Description |
| --- | --- | --- | --- |
| `action` | `string` | yes | The action to check |
| `resource` | `string` | yes | The resource type to check |
| `resourceId` | `string` | no | Specific resource instance |
| `scope` | `string` | no | Scope for the check |
| `children` | `ReactNode` | yes | Rendered when allowed |
| `fallback` | `ReactNode` | no | Rendered when denied (defaults to null) |

`Cannot` has the same props except `fallback`. It renders `children` when the permission is denied, and `null` otherwise. Both components read `useAccess()`, so both are subject to the missing-provider behavior above.

### usePermissions hook

Fetch permissions from a server endpoint on the client side. Useful for SPAs without server-side rendering.

```tsx
import { usePermissions } from '@/lib/access'

function App({ userId }: { userId: string }) {
  const { can, loading, error, refetch } = usePermissions(
    () => fetch(`/api/me/permissions?u=${userId}`).then(r => r.json()),
    [userId] // dependency array, like useEffect
  )

  if (loading) return <Spinner />
  if (error) return <ErrorMessage error={error} onRetry={refetch} />

  return (
    <div>
      {can('create', 'post') && <NewPostButton />}
    </div>
  )
}
```

The hook returns:

| Property | Type | Description |
| --- | --- | --- |
| `permissions` | `PermissionMap` | The fetched map. A frozen empty map until the first load lands, and again for the whole of every reload |
| `can` / `cannot` | `(action, resource, resourceId?, scope?) -> boolean` | Permission checkers |
| `allowedActions` | `(resource) -> string[]` | Actions the map allows on that resource type |
| `hasAnyOn` | `(resource) -> boolean` | Whether the map allows anything on that resource type |
| `loading` | `boolean` | Starts `true` |
| `error` | `Error or null` | Normalised: a rejection carrying a string or a `Response` still arrives as an `Error` |
| `refetch` | `() -> Promise<void>` | Reload; resolves when the run settles, superseded or not |

`deps` defaults to `[]` and decides **when** a reload happens, not what gets fetched. A
`fetchFn` closing over a subject id with `deps: []` never reloads when that id changes -- list
whatever the fetcher closes over. `refetch()` is independent of `deps`: it runs whichever
`fetchFn` the component is rendering with at the moment it is called, so on an account switch
it fetches the new subject.

Overlapping loads are handled by a monotonic run id compared on settle, not a cancelled flag,
so an earlier load that resolves last is discarded rather than landing on top of a newer one.
Unmount is a separate guard. Requests are not aborted; late results are ignored.

Every reload resets the map to empty and clears `error` **before** awaiting the fetch, so
during any reload -- and after a failed one -- everything is denied. That is deliberate: a
refetch is treated as a different subject until proven otherwise, and holding the previous map
would answer with the last user's grants across a sign-out or an account switch. Two
consequences worth designing for:

1. `cannot()` is `!can()`, so a `<Cannot>` denial message renders for the whole in-flight
   window. Gate negative-space UI on `loading`.
2. `usePermissions` and `<Can>` are not connected -- `Can` reads the context, the hook returns
   a plain object. Feed one into the other yourself, and guard on `loading` first, or the
   provider is briefly populated with an empty map and every `<Can>` renders its fallback.

### Standalone checker

For code outside React components (utilities, event handlers, tests), use `createIamPermissionChecker`. It takes a `PermissionMap` and returns `can`, `cannot`, `allowedActions`, `hasAnyOn` and the raw `permissions`.

```typescript
import { createIamPermissionChecker } from '@gentleduck/iam/client/react'

const checker = createIamPermissionChecker(permissionMap)
checker.can('delete', 'post')         // boolean
checker.cannot('manage', 'team')      // boolean
checker.allowedActions('post')        // string[]
checker.permissions                    // the caller's own map, by reference
```

Unlike `AccessProvider`, this function does not copy. Every check reads the live argument, so
writing into that map afterwards does change what `can()` answers. Hand it a map nothing else
holds, or hand it the same map you would hand the provider and treat both as immutable.

## Vue

```
import { createIamVueAccess, IAM_ACCESS_INJECTION_KEY } from '@gentleduck/iam/client/vue'
```

### Setup

Create the Vue access control system by passing Vue's reactive utilities. This avoids a hard Vue version dependency.

```typescript
// lib/access.ts
import { ref, computed, inject, provide, defineComponent, h } from 'vue'
import { createIamVueAccess } from '@gentleduck/iam/client/vue'

export const {
  createAccessState,
  provideAccess,
  useAccess,
  usePermissions,
  createAccessPlugin,
  Can,
  Cannot,
  IAM_ACCESS_INJECTION_KEY,
} = createIamVueAccess({ ref, computed, inject, provide, defineComponent, h })
```

Call the factory once and export the result. `computed` and `h` are required by the injected
interface but unused by the current implementation. `IAM_ACCESS_INJECTION_KEY` is
`Symbol.for('@gentleduck/iam:access')` rather than a plain symbol, so a mixed ESM/CJS load
still has `provide` and `inject` agreeing on one key.

### Plugin installation

Install the plugin in your Vue app to make permissions available to all components.

```typescript
// main.ts
import { createApp } from 'vue'
import { createAccessPlugin } from '@/lib/access'
import App from './App.vue'

const app = createApp(App)

// permissions is a PermissionMap from your server
app.use(createAccessPlugin(permissions))

app.mount('#app')
```

The plugin also registers `$can` and `$cannot` as global properties for direct template use:

```html
<button v-if="$can('delete', 'post')">Delete</button>
```

### Composable

Use `useAccess` in any component within the provider tree.

```vue
<script setup lang="ts">
import { useAccess } from '@/lib/access'

const { can, cannot, permissions, update } = useAccess()
</script>

<template>
  <div>
    <button v-if="can('update', 'post')">Edit</button>
    <button v-if="can('delete', 'post')">Delete</button>
    <p v-if="cannot('manage', 'team')">Contact an admin to manage teams.</p>
  </div>
</template>
```

The composable returns:

| Property | Type | Description |
| --- | --- | --- |
| `permissions` | `Ref<PermissionMap>` | Reactive permission map |
| `can` | `(action, resource, resourceId?, scope?) -> boolean` | Check if allowed |
| `cannot` | `(action, resource, resourceId?, scope?) -> boolean` | Check if denied |
| `allowedActions` | `(resource) -> string[]` | Actions the map allows on that resource type |
| `hasAnyOn` | `(resource) -> boolean` | Whether the map allows anything on that resource type |
| `update` | `(newPerms) -> void` | Replace the permission map (triggers reactivity) |

`useAccess()` **always throws** when nothing was provided, with no environment gate. Vue does
not copy the map in either direction: `createAccessState` puts your object straight into the
`ref` and `update` assigns the object you pass. Writing into that object changes what `can()`
answers and triggers no reactivity, because the `ref` only sees writes made through
`permissions.value`. Replace the map; never edit it.

### Can and Cannot components

Declarative permission gates using slots.

```vue
<template>
  <Can action="delete" resource="post">
    <button>Delete Post</button>
  </Can>

  <Can action="read" resource="analytics">
    <template #default>
      <AnalyticsPanel />
    </template>
    <template #fallback>
      <p>Upgrade to Pro to access analytics.</p>
    </template>
  </Can>

  <Cannot action="create" resource="post">
    <p>You do not have permission to create posts.</p>
  </Cannot>
</template>
```

`Can` renders the default slot when allowed, or the `fallback` slot when denied -- and when denied with no `fallback` slot it returns `undefined`, not `null`. `Cannot` renders its default slot when denied and `null` otherwise. Both call `useAccess()` in `setup`, so both throw outside a provider.

### Manual provide/inject

If you prefer not to use the plugin, call `provideAccess` in a parent component. Useful in
SSR setups where you hydrate permissions per-request instead of at app startup.

```vue
<script setup lang="ts">
import { provideAccess } from '@/lib/access'

// permissions is a PermissionMap from your server
const state = provideAccess(permissions)
// state has the same shape as useAccess(): { permissions, can, cannot, update }
</script>
```

Child components can then call `useAccess()` as usual.

### createAccessState (low-level)

For full control without provide/inject, use `createAccessState` directly. It returns a reactive state object without registering it in the injection system.

```typescript
import { createAccessState } from '@/lib/access'

const state = createAccessState(permissionsFromServer)
state.can('delete', 'post')      // boolean
state.permissions.value            // reactive Ref<PermissionMap>
state.update(newPermissions)       // replaces and triggers reactivity
```

This is returned from `createIamVueAccess()` alongside the other exports.

### Vue usePermissions

Vue's `usePermissions(fetchFn)` answers the same questions as React's, with three differences
that matter. It takes no dependency list. `permissions`, `loading` and `error` are `Ref`s, so
read them with `.value`. And the first load fires **synchronously in the composable body**,
with no lifecycle hook to defer or cancel it -- which is what to watch for under SSR. It
carries the same monotonic supersession guard as React but no unmount guard, so a late
response still writes to the ref of a disposed component.

## Vanilla (framework-agnostic)

```
import { IamAccessClient } from '@gentleduck/iam/client/vanilla'
```

### Basic usage

Create an `IamAccessClient` from a permission map.

```typescript
import { IamAccessClient } from '@gentleduck/iam/client/vanilla'

const access = new IamAccessClient(permissionsFromServer)

access.can('delete', 'post')                     // true
access.cannot('manage', 'billing')                // true
access.can('manage', 'user', undefined, 'admin')  // scoped check
```

### Fetch from server

`fromServer` fetches the URL, parses the JSON response as a `PermissionMap`, and returns a new `IamAccessClient`. A non-2xx status throws `Failed to fetch permissions: {status}` **before** the body is read, so a non-JSON error page never reaches `res.json()` -- and a rejected call gives you a status code and nothing else. Fetch it yourself if you need the error body.

```typescript
const access = await IamAccessClient.fromServer('/api/me/permissions', {
  headers: { Authorization: 'Bearer ' + token },
})

access.can('delete', 'post') // boolean
```

The second argument is a standard `RequestInit` and passes through in full, method included -- this is not GET-only. A `Content-Type: application/json` header is merged in first and your headers merge over it, so passing your own `Content-Type` wins.

### Allowed actions

`allowedActions` scans the permission map and returns a deduplicated array of action strings where the value is `true`. `hasAnyOn` short-circuits and returns as soon as it finds any allowed permission.

```typescript
access.allowedActions('post')  // ['read', 'create', 'update']
access.hasAnyOn('billing')     // false
access.hasAnyOn('post')        // true
```

Both methods handle all four key formats. The `@` on a scope is what makes a 3-part key
unambiguous: `"@org-1:read:post"` is scope + action + resource, while `"read:post:p-42"`
is action + resource + resourceId. Without the marker the two shapes are indistinguishable,
which is why a hand-written `"org-1:read:post"` parses as action `"org-1"` and never
matches.

These helpers suit UI summarization -- navigation menus, toolbar groups, or coarse "does
this user have anything on posts?" checks. They scan the existing `PermissionMap` and do
not replace server-side permission evaluation.

### Reactive updates

Vanilla is the only client that closes both directions: it copies the map in on construction
and on `update`, and copies out on every `permissions` read. Subscribe to changes to trigger
re-renders in any framework. A listener that throws is logged and the remaining listeners
still run.

```typescript
const unsubscribe = access.subscribe((newPermissions) => {
  // Re-render your UI with the new permissions
  rerender()
})

// Update permissions (e.g. after role change)
access.update(newPermissionsFromServer)

// Merge new permissions into existing ones
access.merge({ 'manage:team': true })

// Clean up
unsubscribe()
```

### Integration with other frameworks

The vanilla client works as a foundation for any framework.

**Svelte:**

```typescript
// stores/access.ts
import { writable, derived } from 'svelte/store'
import { IamAccessClient } from '@gentleduck/iam/client/vanilla'

const client = new IamAccessClient(initialPermissions)
const permissions = writable(client.permissions)

client.subscribe((perms) => permissions.set(perms))

export const can = (action: string, resource: string) =>
  derived(permissions, () => client.can(action, resource))
```

**Solid:**

```typescript
import { createSignal } from 'solid-js'
import { IamAccessClient } from '@gentleduck/iam/client/vanilla'

const client = new IamAccessClient(initialPermissions)
const [permissions, setPermissions] = createSignal(client.permissions)

client.subscribe(setPermissions)

export const can = (action: string, resource: string) =>
  () => client.can(action, resource)
```

### IamAccessClient API reference

| Method / Property | Type | Description |
| --- | --- | --- |
| `constructor(perms?)` | `new (PermissionMap?) -> IamAccessClient` | Create from a permission map; the argument is copied in, defaults to an empty map |
| `IamAccessClient.fromServer(url, init?)` | `static async -> IamAccessClient` | Fetch permissions from an endpoint |
| `can(action, resource, resourceId?, scope?)` | `-> boolean` | Check if allowed |
| `cannot(action, resource, resourceId?, scope?)` | `-> boolean` | Check if denied |
| `allowedActions(resource)` | `-> string[]` | List all allowed actions for a resource |
| `hasAnyOn(resource)` | `-> boolean` | Check if any permission exists on a resource |
| `permissions` | `Readonly<PermissionMap>` | A fresh copy on every read, so mutating what you read back changes nothing |
| `update(perms)` | `-> void` | Copy in a replacement and notify listeners with the object you passed |
| `merge(perms)` | `-> void` | Merge new permissions into existing and notify |
| `subscribe(fn)` | `-> () -> void` | Listen for changes, returns unsubscribe function. There is no teardown but that closure -- call it |

## Server-driven pattern

Recommended architecture:

<MermaidDiagram chart={`sequenceDiagram
    participant S as Server
    participant C as Client

    S->>S: 1. Authenticate user
    S->>S: 2. engine.permissions(userId, checks)
    S->>C: 3. Return PermissionMap
    C->>C: 4. Hydrate AccessProvider / plugin / IamAccessClient
    C->>C: 5. can("delete", "post") — instant boolean lookup
    C->>C: 6. <Can action="manage" resource="team"> — render gate`} />

- **Blast radius**: Policies, roles and subject attributes never leave the server; the client sees only booleans for the checks you asked for. It does not make the client trustworthy -- the booleans it holds are editable, and the server still has to authorize the request.
- **Performance**: Client-side checks are instant object lookups. No async operations, no network requests, no engine evaluation.
- **Consistency**: The server is the single source of truth. The client reflects exactly what the server decided.
- **Simplicity**: The client libraries are thin wrappers around a flat object.

### Refreshing permissions

When a user's role changes (promoted, joined an org, feature flag flips), fetch a new permission map from the server and update the client.

**React:**

```tsx
// Re-render the server component (Next.js router.refresh())
// or use usePermissions with a refetch trigger
```

**Vue:**

```typescript
const { update } = useAccess()
const newPerms = await fetch('/api/me/permissions').then(r => r.json())
update(newPerms)
```

**Vanilla:**

```typescript
const newPerms = await fetch('/api/me/permissions').then(r => r.json())
access.update(newPerms) // subscribers are notified automatically
```

  <AccordionItem value="vanilla-client-when">
    <AccordionTrigger>When should I use the vanilla IamAccessClient?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Use it in non-React or non-Vue frontends, Web Components, small islands, or anywhere you want a subscribable
      permission store with <code className="rounded bg-muted px-2 py-1">update()</code>,
      <code className="rounded bg-muted px-2 py-1">merge()</code>, and
      <code className="rounded bg-muted px-2 py-1">subscribe()</code>. Map introspection is no longer a reason to reach
      for it: <code className="rounded bg-muted px-2 py-1">allowedActions()</code> and
      <code className="rounded bg-muted px-2 py-1">hasAnyOn()</code> are on the React context, the Vue access state, and
      every entry point as the standalone <code className="rounded bg-muted px-2 py-1">iamAllowedActions()</code> /
      <code className="rounded bg-muted px-2 py-1">iamHasAnyOn()</code>.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="attribute-sensitive-client-limit">
    <AccordionTrigger>Can a client-side PermissionMap answer live attribute-sensitive questions?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Not in the general case. A permission map is a flattened result for a known set of checks. If the answer depends on
      fresh resource attributes or server-side context, the evaluation still belongs on the server or in a trusted engine runtime.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="resourceid-and-scope">
    <AccordionTrigger>When should I include resourceId or scope in a client-side check?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Include them whenever the server generated a resource-specific or scope-specific permission. If your map contains
      keys like <code className="rounded bg-muted px-2 py-1">@org-1:update:post:post-42</code>, the client must call
      <code className="rounded bg-muted px-2 py-1">can('update', 'post', 'post-42', 'org-1')</code> to hit the same key.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="missing-key-deny">
    <AccordionTrigger>What happens when the permission map is stale or missing a key?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      The clients fail closed and return <code className="rounded bg-muted px-2 py-1">false</code>. That is the right
      default for rendering gates, but it also means you should refresh the permission map after role, scope, or feature
      changes that affect the visible UI.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="allowedactions-granularity">
    <AccordionTrigger>Are allowedActions() and hasAnyOn() safe for record-level decisions?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Not by themselves. They summarize the keys already present in the map for a resource type, which is useful for
      broad UI decisions. Record ownership, fresh attributes, and server-only context still belong in server evaluation.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="manual-key-building">
    <AccordionTrigger>Should I build PermissionMap keys manually?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Prefer <code className="rounded bg-muted px-2 py-1">iamBuildPermissionKey()</code> if you need to compose keys
      outside the shipped clients. It keeps your custom code aligned with the exact key order used by
      <code className="rounded bg-muted px-2 py-1">engine.permissions()</code>, the Next helper, and the vanilla client.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="missing-scope-or-id">
    <AccordionTrigger>What happens if I forget the scope or resourceId when the map only contains a scoped or instance key?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      The lookup misses and returns <code className="rounded bg-muted px-2 py-1">false</code>. The client does not try to
      “best guess” a broader permission from a narrower key, so the shape of your
      <code className="rounded bg-muted px-2 py-1">can(...)</code> call needs to match the shape of the key the server generated.
    </AccordionContent>
