## Overview

Adapters are the storage layer for duck-iam. They implement the `Adapter` interface, which combines three stores:

<MermaidDiagram chart={`flowchart TD
    subgraph Adapter_Interface["Adapter Interface"]
        direction TB
        ADAPTER["Adapter"] --> PS["PolicyStore"]
        ADAPTER --> RS["RoleStore"]
        ADAPTER --> SS["SubjectStore"]

        PS --> PS1["listPolicies()"]
        PS --> PS2["getPolicy(id)"]
        PS --> PS3["savePolicy(policy)"]
        PS --> PS4["deletePolicy(id)"]

        RS --> RS1["listRoles()"]
        RS --> RS2["getRole(id)"]
        RS --> RS3["saveRole(role)"]
        RS --> RS4["deleteRole(id)"]

        SS --> SS1["getSubjectRoles(id)"]
        SS --> SS2["getSubjectScopedRoles(id) -- optional"]
        SS --> SS3["assignRole(id, role, scope?)"]
        SS --> SS4["revokeRole(id, role, scope?)"]
        SS --> SS5["getSubjectAttributes(id)"]
        SS --> SS6["setSubjectAttributes(id, attrs)"]
    end

    subgraph Implementations["Built-in Implementations"]
        direction LR
        MEM["IamMemoryAdapter\nIn-process Maps\nDev / Testing"]
        PRI["IamPrismaAdapter\nPrisma Client\nProduction DB"]
        DRI["IamDrizzleAdapter\nDrizzle ORM\nProduction DB"]
        HTT["IamHttpAdapter\nfetch() calls\nRemote service"]
        RED["IamRedisAdapter\nHashes + sets\nShared storage"]
        FIL["IamFileAdapter\nOne JSON file\nSingle node"]
    end

    Adapter_Interface --> Implementations`} />

- **PolicyStore** -- CRUD for access policies (rules, conditions, combining algorithms)
- **RoleStore** -- CRUD for roles (permissions, inheritance, scopes)
- **SubjectStore** -- role assignments, scoped roles, and subject attributes

Every adapter is fully typed with your application's action, resource, role, and scope types.

```typescript
import { IamEngine } from '@gentleduck/iam'

const engine = new IamEngine({
  adapter: yourAdapter,
  defaultEffect: 'deny',
  cacheTTL: 60,
})
```

## Memory adapter

```
import { IamMemoryAdapter } from '@gentleduck/iam/adapters/memory'
```

Stores everything in `Map` instances. Designed for development, testing, and prototyping. Data does not survive process restarts.

### Basic usage

```typescript
import { IamMemoryAdapter } from '@gentleduck/iam/adapters/memory'

const adapter = new IamMemoryAdapter({
  roles: [
    {
      id: 'admin',
      name: 'Administrator',
      permissions: [
        { action: '*', resource: '*' },
      ],
    },
    {
      id: 'editor',
      name: 'Editor',
      permissions: [
        { action: 'read', resource: '*' },
        { action: 'create', resource: 'post' },
        { action: 'update', resource: 'post' },
        { action: 'delete', resource: 'post' },
      ],
    },
    {
      id: 'viewer',
      name: 'Viewer',
      permissions: [
        { action: 'read', resource: '*' },
      ],
    },
  ],

  policies: [
    {
      id: 'default',
      name: 'Default Policy',
      algorithm: 'deny-overrides',
      rules: [
        {
          id: 'deny-banned',
          effect: 'deny',
          priority: 100,
          actions: ['*'],
          resources: ['*'],
          conditions: {
            all: [{ field: 'subject.attributes.status', operator: 'eq', value: 'banned' }],
          },
        },
        {
          id: 'allow-all',
          effect: 'allow',
          priority: 1,
          actions: ['*'],
          resources: ['*'],
          conditions: { all: [] },
        },
      ],
    },
  ],

  assignments: {
    'user-1': ['admin'],
    'user-2': ['editor'],
    'user-3': ['viewer'],
  },
})
```

### With subject attributes

Pass initial attributes for ABAC-style conditions.

```typescript
const adapter = new IamMemoryAdapter({
  roles: [...],
  assignments: { 'user-1': ['editor'] },
  attributes: {
    'user-1': {
      department: 'engineering',
      level: 3,
      verified: true,
    },
  },
})
```

### Constructor options

| Option | Type | Description |
| --- | --- | --- |
| `roles` | `Role[]` | Initial role definitions |
| `policies` | `Policy[]` | Initial policy definitions |
| `assignments` | `Record<string, string[]>` | Map of subject ID to role IDs |
| `attributes` | `Record<string, Attributes>` | Map of subject ID to attribute objects |

### Behavior details

- **Duplicate assignments**: `assignRole` is idempotent per `(subject, role, scope)`. Calling
  `assignRole('user-1', 'editor')` twice leaves one grant.
- **Unknown roles are refused**: `assignRole` throws when the role id is not stored, and the
  constructor applies the same check -- `roles` is seeded first, then `assignments` through
  the write path's own guard. An init naming a role it does not also define throws instead of
  producing a grant no catalog backs.
- **Attribute merging**: `setSubjectAttributes` shallow-merges per key; keys the patch does
  not name survive. There is no delete. Setting a key to `null` stores `null`, which every
  condition operator then reads as an absent field.
- **Attributes are copied in both directions**: the constructor seed, `getSubjectAttributes`
  and `setSubjectAttributes` all route through `iamCopyAttributes`. Neither the object you
  pass in nor the one you read back stays connected to stored state, so mutating a returned
  array does not reach the store and mutating an argument after the write returns does not
  either.
- **Scoped vs unscoped roles**: stored in the same array, read by two disjoint methods.
  `getSubjectRoles` returns global (unscoped) grants only; `getSubjectScopedRoles` returns the
  scoped ones. Neither is a superset of the other.
- **No `withClient`**: `IamEngine.withTransaction` throws on this adapter.

### When to use

- **Unit tests** -- seed known roles and assignments, assert engine behavior
- **Development** -- get started without a database
- **Prototyping** -- explore the policy model before committing to a schema
- **CI pipelines** -- run integration tests without external dependencies

## Prisma adapter

```
import { IamPrismaAdapter } from '@gentleduck/iam/adapters/prisma'
```

Stores policies, roles, assignments, and subject attributes in your database through Prisma
Client. It looks for the delegates `accessPolicy`, `accessRole`, `accessAssignment` and
`accessSubjectAttr` -- model names, not table names -- and is typed structurally, so this
package takes no dependency on your generated client.

### Required schema

Copy these models from `src/adapters/prisma/schema.prisma` into your own `schema.prisma`. The
`@@map`s point them at the same `iam_*` tables the Drizzle schemas use.

```prisma
model AccessPolicy {
  id          String   @id
  name        String
  description String?
  version     Int      @default(1)
  algorithm   String   @default("deny-overrides")
  rules       Json
  targets     Json?
  createdBy   String?  @map("created_by")
  updatedBy   String?  @map("updated_by")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  @@map("iam_policies")
}

model AccessRole {
  id          String             @id
  name        String
  description String?
  permissions Json
  inherits    String[]           @default([])
  scope       String?
  metadata    Json?
  createdBy   String?            @map("created_by")
  updatedBy   String?            @map("updated_by")
  createdAt   DateTime           @default(now()) @map("created_at")
  updatedAt   DateTime           @updatedAt @map("updated_at")
  assignments AccessAssignment[]

  @@index([scope])
  @@map("iam_roles")
}

model AccessAssignment {
  id        String     @id @default(cuid())
  subjectId String     @map("subject_id")
  roleId    String     @map("role_id")
  scope     String?
  role      AccessRole @relation(fields: [roleId], references: [id], onDelete: Cascade)
  createdBy String?    @map("created_by")
  updatedBy String?    @map("updated_by")
  createdAt DateTime   @default(now()) @map("created_at")
  updatedAt DateTime   @updatedAt @map("updated_at")

  @@unique([subjectId, roleId, scope])
  @@index([subjectId])
  @@index([roleId])
  @@index([subjectId, scope])
  @@map("iam_assignments")
}

model AccessSubjectAttr {
  subjectId String   @id @map("subject_id")
  data      Json
  createdBy String?  @map("created_by")
  updatedBy String?  @map("updated_by")
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("iam_subject_attrs")
}
```

The relation on `AccessAssignment.role` is load-bearing, not decoration: the foreign key is
what makes `assignRole` refuse a role that is not stored, and `onDelete: Cascade` is what makes
`deleteRole` take the grants with it. Without it a role recreated under a reused id hands
itself back to everyone who once held it.

Run `prisma migrate dev` after adding these models.

<Callout type="warning" title="You must replace the unique index Prisma generates">
`scope` is nullable and SQL unique indexes treat NULLs as distinct, so
`@@unique([subjectId, roleId, scope])` does **not** stop a duplicate *unscoped* grant. Prisma
can express neither `NULLS NOT DISTINCT` nor a `coalesce` index, so replace it in a migration:

```sql
-- Postgres 15+
DROP INDEX "iam_assignments_subject_id_role_id_scope_key";
CREATE UNIQUE INDEX "iam_assignments_subject_id_role_id_scope_key"
  ON "iam_assignments" ("subject_id", "role_id", "scope") NULLS NOT DISTINCT;

-- MySQL / SQLite
CREATE UNIQUE INDEX "iam_assignments_subject_id_role_id_scope_key"
  ON "iam_assignments" ("subject_id", "role_id", (coalesce("scope", '')));
```

`assignRole` is a read-then-write -- a nullable column in the composite key means `upsert`
cannot address the row -- and a read cannot make a write atomic. The index is what decides the
outcome. Twenty concurrent identical unscoped grants leave three rows under the index Prisma
generates and exactly one under either replacement.
</Callout>

### Usage

```typescript
import { PrismaClient } from '@prisma/client'
import { IamPrismaAdapter } from '@gentleduck/iam/adapters/prisma'
import { IamEngine } from '@gentleduck/iam'

const prisma = new PrismaClient()
const adapter = new IamPrismaAdapter(prisma)

const engine = new IamEngine({ adapter })
```

One argument, no options object. There is nowhere to wire an `onPolicyError`, which is why
every corrupt-row report this adapter makes goes to `console.warn`. An unreadable role row is
skipped and named; an unreadable policy row is refused and the read throws.

`savePolicy` and `saveRole` upsert, so saving an existing id updates the record rather than
raising a conflict.

This adapter has no `starts_at`, `expires_at` or `attributes` columns, so `assignRole` **throws**
when given `startsAt`, `expiresAt` or `attributes` rather than dropping them. Use the Drizzle
adapter for time-boxed or attributed grants.

### How it maps

| Adapter method | Prisma operation |
| --- | --- |
| `listPolicies()` | `accessPolicy.findMany()` |
| `getPolicy(id)` | `accessPolicy.findUnique({ where: { id } })` |
| `savePolicy(p)` | `accessPolicy.upsert(...)` |
| `deletePolicy(id)` | `accessPolicy.deleteMany({ where: { id } })` -- `delete` raises `P2025` on a missing row, `deleteMany` no-ops |
| `listRoles()` | `accessRole.findMany()` |
| `getRole(id)` | `accessRole.findUnique({ where: { id } })` |
| `saveRole(r)` | `accessRole.upsert(...)` |
| `deleteRole(id)` | `accessRole.deleteMany({ where: { id } })`; the FK cascade removes the grants |
| `getSubjectRoles(id)` | `accessAssignment.findMany(...)`, filtered for a null scope -- global grants only |
| `getSubjectScopedRoles(id)` | Same query, filtered for non-null scope |
| `assignRole(id, role, scope?)` | read, then `accessAssignment.create(...)`; the `P2002` a racing writer causes is treated as success |
| `revokeRole(id, role, scope?)` | `accessAssignment.deleteMany(...)` |
| `getSubjectAttributes(id)` | `accessSubjectAttr.findUnique(...)` |
| `setSubjectAttributes(id, attrs)` | `accessSubjectAttr.upsert(...)` (merges with existing) |

## Drizzle adapter

```
import { IamDrizzleAdapter } from '@gentleduck/iam/adapters/drizzle'
```

One dialect-neutral class covers PostgreSQL, MySQL and SQLite. Which dialect you are on is a
config field, not a different class.

### Table definitions

The package ships the schema for all three dialects, so you import the tables rather than
declaring them:

```typescript
import { iamAssignments, iamPolicies, iamRoles, iamSubjectAttrs } from '@gentleduck/iam/adapters/drizzle/pg'
```

`@gentleduck/iam/adapters/drizzle/mysql` and `@gentleduck/iam/adapters/drizzle/sqlite` export
the same four names, so changing dialect is a change of import path plus the `dialect` field
below. Point `drizzle-kit generate` at the module for your migration.

The adapter reads whatever table objects you hand it, so you can aim it at your own tables --
but then the column *property* names are the contract:

```
policies:    id name description version algorithm rules targets createdBy updatedBy createdAt updatedAt
roles:       id name description permissions inherits scope metadata createdBy updatedBy createdAt updatedAt
assignments: id subjectId roleId scope startsAt expiresAt attributes createdBy updatedBy createdAt updatedAt
attrs:       subjectId data createdBy updatedBy createdAt updatedAt
```

Two constraints on the assignments table are easy to lose when hand-writing DDL and are
load-bearing when lost. A foreign key on `role_id` to `iam_roles(id)` with `ON DELETE CASCADE`
is what makes `assignRole` refuse an unstored role and `deleteRole` take the grants with it. A
unique index over `(subject_id, role_id, scope)` has to collapse NULLs -- `NULLS NOT DISTINCT`
on Postgres, an index over `coalesce(scope, '')` on MySQL and SQLite -- because a plain unique
index treats NULLs as distinct and so does not stop two identical unscoped grants.

### Usage

```typescript
import { and, eq, isNull, or } from 'drizzle-orm'
import { drizzle } from 'drizzle-orm/node-postgres'
import { IamDrizzleAdapter } from '@gentleduck/iam/adapters/drizzle'
import { iamAssignments, iamPolicies, iamRoles, iamSubjectAttrs } from '@gentleduck/iam/adapters/drizzle/pg'
import { IamEngine } from '@gentleduck/iam'

const adapter = new IamDrizzleAdapter({
  db: drizzle(pool),
  tables: { policies: iamPolicies, roles: iamRoles, assignments: iamAssignments, attrs: iamSubjectAttrs },
  ops: { and, eq, isNull, or },
  // dialect defaults to 'pg', json defaults to 'native' -- both correct here
})

const engine = new IamEngine({ adapter })
```

### Constructor config

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `db` | Drizzle database instance | -- | Anything with `select`, `insert`, `update`, `delete` |
| `tables.policies` | Drizzle table | -- | Policy table reference |
| `tables.roles` | Drizzle table | -- | Role table reference |
| `tables.assignments` | Drizzle table | -- | Assignment table reference |
| `tables.attrs` | Drizzle table | -- | Subject attributes table reference |
| `ops.eq` | Drizzle `eq` | -- | Required |
| `ops.and` | Drizzle `and` | -- | Required |
| `ops.isNull` | Drizzle `isNull` | absent | Optional. Gates `updateAssignmentScope` entirely |
| `ops.or` | Drizzle `or` | absent | Optional. Collapses `revokeRoleMany` into one `DELETE` |
| `dialect` | `'pg'`, `'mysql'` or `'sqlite'` | `'pg'` | Only `'mysql'` changes behavior |
| `json` | `'native'` or `'string'` | `'native'` | Write encoding for JSON payload columns |
| `onPolicyError` | `(err, ctx) -> void` | `console.warn` | Fires for every malformed row |

Pass all four operators. Neither optional one can be derived -- `eq(col, null)` is not
`IS NULL`, and there is no way to build an `OR` from `eq` and `and` -- so omitting them is a
correct but degraded path, and the adapter warns once per process at construction. Without
`isNull`, `updateAssignmentScope` returns `false` and the engine falls back to revoke +
assign: two writes, and a window in which the subject holds nothing.

<Callout type="warning" title="dialect and json are not inferred">
Nothing inspects `db` or the tables. On MySQL, omitting `dialect: 'mysql'` sends
`onConflictDoUpdate()` and `onConflictDoNothing()` to an insert builder that has neither, so
every write path fails at runtime while the delete paths keep working -- the symptom is "saves
fail, revokes succeed", not a dead adapter. On the shipped SQLite schema, `json: 'string'` is
required because every payload column is TEXT; nothing checks the combination, so a missed
`json` field reaches the driver as a live object and whatever your driver does with it is the
whole of the diagnosis.
</Callout>

### JSON handling

`json` decides the **write** encoding: `'native'` hands the driver the object, which is what
Postgres `jsonb` and MySQL `json` columns want; `'string'` serialises first, which is what the
shipped SQLite schema's TEXT columns want. The read path accepts both shapes on every dialect,
so switching the field is migration-safe.

## HTTP adapter

```
import { IamHttpAdapter } from '@gentleduck/iam/adapters/http'
```

Delegates all storage operations to a remote API. Use it when:

- Your access engine runs on a dedicated service
- You want to share policies across multiple applications
- Your client-side code needs to evaluate permissions against a server

### Usage

```typescript
import { IamHttpAdapter } from '@gentleduck/iam/adapters/http'
import { IamEngine } from '@gentleduck/iam'

const adapter = new IamHttpAdapter({
  baseUrl: 'https://api.example.com/access',
  allowedHosts: ['api.example.com'],
  headers: {
    Authorization: 'Bearer ' + serviceToken,
  },
})

const engine = new IamEngine({ adapter })
```

### Dynamic headers

Pass a function to compute headers per-request. Useful for rotating tokens or per-request context.

```typescript
const adapter = new IamHttpAdapter({
  baseUrl: 'https://api.example.com/access',
  headers: async () => ({
    Authorization: 'Bearer ' + await getServiceToken(),
    'X-Request-Id': crypto.randomUUID(),
  }),
})
```

### Custom fetch

Provide your own fetch implementation for environments without a global `fetch`, or to add middleware like logging or retries.

```typescript
import { IamHttpAdapter } from '@gentleduck/iam/adapters/http'

const adapter = new IamHttpAdapter({
  baseUrl: 'https://api.example.com/access',
  fetch: async (url, init) => {
    console.log('Access API request:', url)
    const res = await globalThis.fetch(url, init)
    console.log('Access API response:', res.status)
    return res
  },
})
```

### API endpoints

The HTTP adapter expects these REST endpoints on your server:

| Method | Path | Description |
| --- | --- | --- |
| GET | /policies | List all policies |
| GET | /policies/:id | Get a single policy |
| PUT | /policies | Create or update a policy |
| DELETE | /policies/:id | Delete a policy |
| GET | /roles | List all roles |
| GET | /roles/:id | Get a single role |
| PUT | /roles | Create or update a role |
| DELETE | /roles/:id | Delete a role |
| GET | /subjects/:id/roles | Get a subject's roles |
| GET | /subjects/:id/scoped-roles | Get a subject's scoped roles |
| POST | /subjects/:id/roles | Assign a role (body: `{ roleId, scope? }`) |
| DELETE | /subjects/:id/roles/:roleId | Revoke a role (query: `?scope=...`) |
| GET | /subjects/:id/attributes | Get subject attributes |
| PATCH | /subjects/:id/attributes | Update subject attributes (body: attribute object) |

`GET /subjects/:id/roles` must return **unscoped** role ids only; the scoped ones belong to
`/scoped-roles`. `PATCH /subjects/:id/attributes` merges, it does not replace. Two obligations
the adapter cannot enforce for you and the contract still holds you to: `DELETE /roles/:id`
must strip the deleted role from every subject's assignments, and `POST /subjects/:id/roles`
must answer 4xx when `roleId` names no stored role. The adapter surfaces the non-2xx as a
throw.

The built-in Express `iamAdminRouter` covers part of this admin surface, but it does **not**
implement the full HTTP adapter contract. If you want to use `IamHttpAdapter`, either implement
the complete endpoint set manually or extend the admin router with the missing item lookups,
scoped-role reads, and subject-attribute endpoints.

### Error handling

A non-2xx response throws `[@gentleduck/iam:http] HTTP {status}: {body}`, with the body read to
a 4 KB cap and the message truncated to 200 characters. A 404 on `GET /policies/:id` or
`GET /roles/:id` is not an error -- it is `null`.

Transient failures **are** retried: a status `>= 500`, a network error, or the `AbortError`
from a per-request timeout. A 4xx is never retried. The delay starts at `backoffMs` and
doubles per retry, capped at 60 s, plus jitter of up to `min(backoffMs, 5000)` ms. After `circuitBreakerThreshold` consecutive transient failures the
circuit opens and further requests reject immediately until `circuitBreakerCooldownMs` has
elapsed, at which point one probe is let through -- success closes the circuit, failure
re-opens it.

A `Content-Type: application/json` header is sent on every request, and headers from `headers`
merge over it. If `headers` is a function, it is awaited before each request. `redirect: 'error'`
is always set.

### Constructor config

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `baseUrl` | `string` | -- | Base URL. Must be `http:` or `https:` and carry no query string or fragment; one trailing slash is stripped |
| `allowedHosts` | `string[]` | none | Host allow-list for `baseUrl`. A bare host matches any port, `host:port` only that port. Omitting it warns once per process |
| `allowPrivateHosts` | `boolean` | `false` | Permits a private or loopback IP literal in `baseUrl`. DNS names are never resolved, so a name pointing at a private address is constrained only by `allowedHosts` |
| `headers` | `Record or () -> Record or Promise` | `{}` | Static or dynamic headers. This is the whole of the auth surface |
| `fetch` | `typeof fetch` | `globalThis.fetch` | Custom fetch implementation |
| `timeoutMs` | `number` | `5000` | Per-request timeout. `0` relies on the engine's `adapterTimeoutMs` alone |
| `retries` | `number` | `2` | Retries on transient failures, so 3 attempts in total |
| `backoffMs` | `number` | `100` | Base delay for exponential backoff |
| `circuitBreakerThreshold` | `number` | `5` | Consecutive transient failures that open the circuit. Must be an integer >= 1 |
| `circuitBreakerCooldownMs` | `number` | `30000` | Half-open cooldown |
| `onPolicyError` | `(err, ctx) -> void` | -- | Called for a malformed policy or role row from the API |

Every numeric option is validated at construction rather than defaulted on a falsy read, so a
`NaN` from `Number(process.env.SOMETHING)` on an unset variable throws by name instead of
silently disabling what it configures. `circuitBreakerThreshold: 0` is refused for the same
reason -- it is not an off switch, and there is no off switch. To make the breaker effectively
inert, set a high threshold.

## Custom adapters

Implement the `IamAdapter.IAdapter` interface to connect duck-iam to any storage backend.

<Callout type="info">
duck-iam already ships a Redis adapter (`IamRedisAdapter` from `@gentleduck/iam/adapters/redis`) --
it is not documented on this page yet. The example below builds a Redis-backed adapter from
scratch purely to illustrate the `IamAdapter.IAdapter` shape; reach for the shipped `IamRedisAdapter`
in real projects instead of writing this one.
</Callout>

### The Adapter interface

Members marked `?` are optional; everything else is required.

```typescript
import type { AccessControl, IamAdapter, IamPrimitives, IamRequest } from '@gentleduck/iam'

interface CustomAdapter<TAction extends string, TResource extends string, TRole extends string, TScope extends string>
  extends IamAdapter.IAdapter<TAction, TResource, TRole, TScope> {
  // PolicyStore
  listPolicies(opts?: IamAdapter.IReadOptions): Promise<AccessControl.IPolicy<TAction, TResource, TRole>[]>
  getPolicy(id: string, opts?: IamAdapter.IReadOptions): Promise<AccessControl.IPolicy<TAction, TResource, TRole> | null>
  savePolicy(policy: AccessControl.IPolicy<TAction, TResource, TRole>, opts?: IamAdapter.IActorOptions): Promise<void>
  deletePolicy(id: string): Promise<void>

  // RoleStore
  listRoles(opts?: IamAdapter.IReadOptions): Promise<AccessControl.IRole<TAction, TResource, TRole, TScope>[]>
  getRole(id: string, opts?: IamAdapter.IReadOptions): Promise<AccessControl.IRole<TAction, TResource, TRole, TScope> | null>
  saveRole(role: AccessControl.IRole<TAction, TResource, TRole, TScope>, opts?: IamAdapter.IActorOptions): Promise<void>
  deleteRole(id: string): Promise<void>

  // SubjectStore
  getSubjectRoles(subjectId: string, opts?: IamAdapter.IReadOptions): Promise<TRole[]>
  getSubjectScopedRoles?(subjectId: string, opts?: IamAdapter.IReadOptions): Promise<IamRequest.IScopedRole<TRole, TScope>[]>
  assignRole(subjectId: string, roleId: TRole, scope?: TScope, opts?: IamAdapter.IAssignOptions): Promise<void>
  revokeRole(subjectId: string, roleId: TRole, scope?: TScope, opts?: IamAdapter.IRevokeOptions): Promise<void>
  updateAssignmentScope?(
    subjectId: string,
    roleId: TRole,
    fromScope: TScope | undefined,
    toScope: TScope | undefined,
    actor?: string,
  ): Promise<boolean>
  assignRoleMany?(rows: readonly IamAdapter.IAssignRow<TRole, TScope>[]): Promise<readonly number[] | null>
  revokeRoleMany?(rows: readonly IamAdapter.IRevokeRow<TRole, TScope>[]): Promise<readonly number[] | null>
  getSubjectGrantBoundary?(subjectId: string, opts?: IamAdapter.IReadOptions): Promise<number | null>
  getSubjectAttributes(subjectId: string, opts?: IamAdapter.IReadOptions): Promise<IamPrimitives.Attributes>
  setSubjectAttributes(subjectId: string, attrs: IamPrimitives.Attributes, opts?: IamAdapter.IActorOptions): Promise<void>

  // Transactions
  withClient?(client: unknown): IamAdapter.IAdapter<TAction, TResource, TRole, TScope>
}
```

**The optional members, and what omitting each one costs you:**

| Member | Omitting it means |
|---|---|
| `getSubjectScopedRoles` | Scoped assignments are treated as empty; only global role evaluation happens. |
| `updateAssignmentScope` | Moving a grant between scopes falls back to revoke-then-assign, which is not atomic. |
| `assignRoleMany` / `revokeRoleMany` | Batch admin calls loop one row at a time instead of issuing one statement. Return `null` to say "written, but I cannot report which rows moved". |
| `getSubjectGrantBoundary` | The engine cannot cap a cached subject at its next grant transition, so a time-boxed grant stays visible for the rest of `cacheTTL`. Only the drizzle adapter implements it -- only its schema has `starts_at` / `expires_at`. |
| `withClient` | This adapter cannot join a transaction, and `IamEngine.withTransaction` **throws** rather than silently leaving writes outside the caller's transaction. The memory, file, redis and http adapters all omit it — none has a transaction to join. |

**`opts` on the reads is not decoration.** `IReadOptions` carries the
`AbortSignal` the engine derives from `IConfig.adapterTimeoutMs`. Ignoring it is
not a request leak — the engine races every adapter call against
`adapterTimeoutMs` itself, so the request thread is released either way. What an
ignoring adapter loses is *upstream* cancellation: the query keeps running to
completion and its result is thrown away. Of the six shipped adapters, only
`IamHttpAdapter` honors the signal; if your backend can cancel, plumb it through.

`IAssignOptions` carries the per-grant extras `assignRole` accepts: `startsAt`, `expiresAt`
and `attributes`. Only the drizzle adapter has columns for them. An adapter that cannot store
one must **throw and name it**, never accept and drop it -- a break-glass grant issued with a
one-hour expiry against an adapter that discards it is permanent, and the batch API still
reports it applied.

### Example: a from-scratch Redis-backed adapter

```typescript
import type { AccessControl, IamAdapter } from '@gentleduck/iam'
import type { Redis } from 'ioredis'

export class MyRedisAdapter implements IamAdapter.IAdapter {
  constructor(private redis: Redis, private prefix = 'iam:') {}

  private key(type: string, id?: string) {
    return id ? `${this.prefix}${type}:${id}` : `${this.prefix}${type}`
  }

  async listPolicies(): Promise<AccessControl.IPolicy[]> {
    const keys = await this.redis.keys(this.key('policy', '*'))
    const results = await Promise.all(keys.map(k => this.redis.get(k)))
    return results.filter(Boolean).map(r => JSON.parse(r!))
  }

  async getPolicy(id: string): Promise<AccessControl.IPolicy | null> {
    const raw = await this.redis.get(this.key('policy', id))
    return raw ? JSON.parse(raw) : null
  }

  async savePolicy(p: AccessControl.IPolicy): Promise<void> {
    await this.redis.set(this.key('policy', p.id), JSON.stringify(p))
  }

  async deletePolicy(id: string): Promise<void> {
    await this.redis.del(this.key('policy', id))
  }

  // ... implement remaining methods for roles and subjects
}
```

### Testing custom adapters

Use `IamMemoryAdapter` as a reference implementation. Your adapter should behave identically for the same inputs.

1. Seed your adapter with known roles, policies, and assignments
2. Create an engine with your adapter
3. Assert that `engine.can()` returns the expected results
4. Test edge cases: missing subjects, empty roles, scoped vs unscoped assignments

```typescript
import { IamEngine } from '@gentleduck/iam'
import { YourAdapter } from './your-adapter'

const adapter = new YourAdapter(/* config */)

// Seed
await adapter.saveRole({
  id: 'editor',
  name: 'Editor',
  permissions: [
    { action: 'read', resource: '*' },
    { action: 'update', resource: 'post' },
  ],
})
await adapter.assignRole('user-1', 'editor')

// Test
const engine = new IamEngine({ adapter })
const canUpdate = await engine.can('user-1', 'update', { type: 'post', attributes: {} })
const canDelete = await engine.can('user-1', 'delete', { type: 'post', attributes: {} })

assert(canUpdate === true)
assert(canDelete === false)
```

## Choosing an adapter

| Adapter | Use case | Persistence | Dependencies |
| --- | --- | --- | --- |
| **Memory** | Dev, testing, prototyping | None (in-process) | None |
| **Prisma** | Production apps using Prisma | Database (any Prisma-supported) | `@prisma/client` |
| **Drizzle** | Production apps using Drizzle | Database (PG, MySQL, SQLite) | `drizzle-orm` |
| **HTTP** | Microservices, client-server split | Remote API | None (uses `fetch`) |
| **Redis** | Shared cache-speed storage across instances | Redis | `ioredis` (or compatible) |
| **File** | Single-node deployments, local JSON persistence | Local filesystem | None |
| **Custom** | Any other storage backend | Your choice | Your choice |

All adapters are interchangeable. Start with the memory adapter during development and switch to Prisma or Drizzle in production without changing any engine or middleware code.

<Callout type="info">
`IamRedisAdapter` (`@gentleduck/iam/adapters/redis`) and `IamFileAdapter` (`@gentleduck/iam/adapters/file`)
ship with the package but don't have a dedicated section on this page yet -- see their source
under `packages/duck-iam/src/adapters/{redis,file}` for constructor options in the meantime.
</Callout>

  <AccordionItem value="adapter-responsibility">
    <AccordionTrigger>What does an adapter actually do in duck-iam?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      An adapter is the persistence layer. It loads and stores policies, roles, role assignments, scoped assignments,
      and subject attributes. The engine owns evaluation, policy combination, explain traces, and decision logic.

  <AccordionItem value="memory-persistence">
    <AccordionTrigger>Does IamMemoryAdapter persist anything?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      No. It stores everything in process memory. Restarting the process resets policies, roles, assignments, and
      attributes, which is why it is best for tests, demos, and local development.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="memory-scoped-seed">
    <AccordionTrigger>Can I seed scoped assignments in IamMemoryAdapter constructor input?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Not directly. Constructor assignment seeding is unscoped. For scoped assignments, create the adapter first and then
      call <code className="rounded bg-muted px-2 py-1">assignRole(subjectId, roleId, scope)</code>.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="existing-database">
    <AccordionTrigger>Can I use my existing database instead of a dedicated auth database?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Yes. duck-iam only needs four storage areas for policies, roles, assignments, and subject attributes. Those can live
      alongside the rest of your application schema.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="prisma-vs-drizzle">
    <AccordionTrigger>How do IamPrismaAdapter and IamDrizzleAdapter differ in practice?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Prisma expects named models and lets Prisma handle JSON columns natively. Drizzle expects you to wire the tables and
      query operators explicitly, and the adapter serializes or parses JSON fields for you.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="attribute-merge-behavior">
    <AccordionTrigger>Do adapters merge subject attributes or replace them?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      The built-in adapters merge incoming attributes into the current subject attribute map. This lets you patch a few
      attributes without rewriting the entire stored object.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="duplicate-assignment-behavior">
    <AccordionTrigger>How are duplicate role assignments handled?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Assignment is idempotent per subject, role and scope on every adapter. Memory, file and Redis check before writing;
      Drizzle uses a conflict-safe insert against a unique index that collapses NULL scopes; Prisma reads then writes and
      treats the unique-constraint violation a racing writer causes as success. On Prisma the index Prisma generates does
      not collapse NULLs, so you have to replace it in a migration -- otherwise concurrent identical unscoped grants leave
      duplicate rows.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="http-adapter-local-eval">
    <AccordionTrigger>Does IamHttpAdapter move policy evaluation to the server?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      No. IamHttpAdapter fetches authorization data over HTTP, but the consuming engine still evaluates permissions locally.
      Use it when you want shared storage behind a service boundary, not when you want to outsource evaluation entirely.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="http-dynamic-headers">
    <AccordionTrigger>Can IamHttpAdapter attach auth headers dynamically?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Yes. The <code className="rounded bg-muted px-2 py-1">headers</code> option can be a static object or an async
      function, which makes it suitable for short-lived bearer tokens and per-request auth state.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="memory-to-db-migration">
    <AccordionTrigger>Can I start with IamMemoryAdapter and move to Prisma, Drizzle, or HTTP later?</AccordionTrigger>
    <AccordionContent className="text-muted-foreground">
      Yes. That is one of the intended adoption paths. The engine and builder APIs stay the same; the main migration work

    </AccordionContent>

  <AccordionItem value="scoped-role-contract">
    <AccordionTrigger>What should a scoped-role capable adapter guarantee?</AccordionTrigger>

      It should keep global role assignments and scoped assignments conceptually separate. Global assignments belong in
      <code className="rounded bg-muted px-2 py-1">getSubjectRoles()</code>. Scope-bound assignments belong in
      <code className="rounded bg-muted px-2 py-1">getSubjectScopedRoles()</code> so the engine can merge them only for
      matching request scopes.
    </AccordionContent>

    <AccordionContent className="text-muted-foreground">

      <code className="rounded bg-muted px-2 py-1">getSubjectScopedRoles()</code> so the engine can merge them only when
      the request scope matches.
    </AccordionContent>
