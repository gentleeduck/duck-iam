## Overview

`@gentleduck/iam` and `@gentleduck/auth` both expose `withTransaction(tx)`. It returns a view
of the engine bound to a transaction handle you own. The handle is opaque to the library and
is handed straight back to your adapter, so the engine never learns what driver you use.

The two packages deliberately share one sequence: bind, do the work, keep the announcements
until the commit lands. They do not share a `pending` type -- the packages do not depend on
each other, and the two `flush()` contracts differ in ways the sections below spell out.

<MermaidDiagram chart={`flowchart TB
    OPEN["db.transaction(tx)"] --> BIND["engine.withTransaction(tx)"]
    BIND --> WRITE["Writes and reads on the bound view"]
    WRITE --> OWN["Your own SQL on the same tx"]
    OWN --> DECIDE{"Commit or rollback"}
    DECIDE -->|commit| FLUSH["pending.flush()"]
    DECIDE -->|rollback| DROP["pending discarded"]
    FLUSH --> OUT["Events published, caches invalidated, fleet notified"]
    DROP --> NOTHING["Nothing announced"]`} />

## duck-auth

```typescript
let pending
await db.transaction(async (tx) => {
  const auth = engine.withTransaction(tx)
  await auth.identities.softDelete(identityId)
  await auth.sessions.revokeAllForIdentity(identityId)
  await tx.delete(users).where(eq(users.id, identityId))
  pending = auth.pending
})
await pending.flush()
```

Nested calls inherit the transaction. `auth.flows.completeAccountDeletion()` reaches
`identities.softDelete`, `sessions.revokeAllForIdentity` and `credentials.delete`, and all
three land on your transaction rather than on the engine's own connection.

Reads are bound too, so a read inside the transaction sees that transaction's uncommitted
writes.

### Events wait for the commit

Events do not fire inside a transaction. They buffer in `pending` and publish when you call
`flush()`, so a rolled-back deletion never appears in the audit trail as a completed one.

- `pending.flush()` publishes everything buffered, in emit order, then empties the buffer. It
  answers `{ published, failed }`. Calling it twice publishes nothing the second time, and
  `published: 0` is how you tell the second call from the first.
- `pending.discard()` drops the buffer for an explicit rollback path and answers
  `{ discarded }`.
- `pending.peek()` inspects the buffer without draining it.
- `pending.size` is the number of events still waiting.

**`flush()` never rejects.** A listener that throws does not stop the drain: every buffered
event is attempted and the errors come back in `failed`. That is deliberate. `flush` runs
*after* your transaction committed, and it empties the buffer either way, so there is nothing
a rejection could ask you to retry -- and throwing would hand a committed write back as a
failure whose one promise, that the write did not happen, would be false. The write happened;
some announcement of it did not. Log the second and still answer 200, or write
`if (failed.length) throw new AggregateError(failed)` if you want the harsher shape.

### What is and isn't transactional

| Surface | In a transaction? | On rollback |
|---|---|---|
| `identities`, `sessions`, `credentials` -- writes and reads | yes | undone |
| `flows.*`, including nested facet calls | yes | undone |
| `mfa`, `apiKeys`, `passwords` credential writes | yes | undone |
| `orgs` | interface ready, no shipped SQL adapter | n/a |
| events | buffered in `pending` | never published |
| channel sends such as verification mail | no, sent immediately | mail already delivered |
| `limiter` counters | no | token stays consumed |
| `idempotency` records | no | record stands |
| `hijack` and `anomaly` scoring | no | scores stand |

<Callout type="info">
The last four are guards. They decide *whether* to do the work, they write nothing to SQL,
and they are not reachable on the bound view at all -- reach them on the engine itself. This
is deliberate: an attacker who can force a rollback must not be able to refund the attempts
it cost, and a caller whose transaction failed must not be able to clear its idempotency
record and silently re-run under the old key.
</Callout>

A flow that sends mail should be called outside a transaction, or split so the send happens
after the commit. No rollback can retract a delivered email.

## duck-iam

```typescript
let pending
await db.transaction(async (tx) => {
  const perms = engine.withTransaction(tx)
  await perms.admin.assignRole(userId, 'admin', orgId)
  await tx.insert(members).values({ userId, orgId })
  pending = perms.pending
})
await pending.flush()
```

Writes go through `.admin`, the same interface as `engine.admin`, so there is one write
surface rather than two.

### Transaction-local caches

Reads on the bound view run against caches created for that transaction alone. An empty
cache always misses through to the transaction-bound adapter, which is what makes a
read-after-write inside the transaction correct. The shared engine keeps answering from its
own warm caches, which the transaction never pollutes.

Cache invalidations -- including the `config.invalidator` fleet broadcast -- buffer in
`pending`, de-duplicated, and fire on `flush()`. A rolled-back grant therefore never evicts
another node's cache for a write that did not happen.

Mutation events buffer alongside them and are **not** de-duplicated: two grants of the same
role are two entries in the history, where two invalidations of the same cache key are one
job. `flush()` applies the invalidations first, then emits the events, so a consumer reacting
to an event already reads post-invalidation caches. `pending.peek()` inspects the invalidation
buffer and `pending.peekMutations()` the event buffer; `size` and `mutationSize` count them
separately.

duck-iam's `flush()` resolves to `void` and **does** raise an `AggregateError` -- the opposite
of duck-auth's contract, and for the opposite reason. Entries whose target threw stay buffered,
so a retry re-applies exactly those; a cache that was not evicted is a wrong answer waiting to
be served, which is worth asking the caller to retry. A throwing `onMutation` hook is the one
exception: it is an observer, so it is logged and skipped rather than left buffered.

<Callout type="info">
The bound view drops the invalidator entirely rather than reusing the parent's. A facade
built per transaction that subscribed would leak a subscription every time. Buffered entries
broadcast through the parent engine on `flush()`, after the commit.
</Callout>

## Adapter support

`withTransaction` needs an adapter that can re-make itself against your driver client, which
it declares by implementing `withClient`.

| Package | Adapters that can join a transaction | Adapters that cannot |
|---|---|---|
| `@gentleduck/auth` | drizzle pg, mysql, sqlite, and any bridge built with `createSqlStores` | memory, redis, valkey |
| `@gentleduck/iam` | drizzle, prisma | memory, file, redis, http |

An adapter that cannot join makes `withTransaction` throw, naming the store, rather than
silently leaving those writes outside your transaction. In duck-auth the error is
`AUTH_MISCONFIGURED` and names the offending store.

An engine with no transaction supplied behaves exactly as it always has: writes go to its
own connection, and events and invalidations fire immediately.

## Batch writes

Batch forms take a list and report per-row outcomes instead of collapsing to `void`.

```typescript
const result = await auth.identities.updateProfileMany([
  { id: a, patch: { displayName: 'A' }, expectedVersion: 3 },
  { id: b, patch: { displayName: 'B' }, expectedVersion: 7 },
])

result.applied  // 1
result.failed   // 1 - duck-auth only; duck-iam has no failure arm
result.outcomes // one entry per input row, in input order
```

The two packages' outcome shapes have diverged, and the difference is not cosmetic.

**duck-auth** outcomes are a discriminated union: `{ id, ok: true, value }` or
`{ id, ok: false, reason, detail? }`, where `reason` is `not-found`, `stale-write` or
`skipped`. Its result carries `applied` and `failed`. An identity id is a real single-field
key there, so keying by `id` works.

**duck-iam** has no failure arm at all. Every outcome is `{ row, ok: true, value }` and the
result carries `applied` -- always `outcomes.length` -- with no `failed`. Both role writes are
idempotent, so a row the statement did not move is still *applied*: the postcondition holds
either way, and calling it a miss would contradict the single-row `assignRole`, which calls
the same case success. The `ok: false` arm existed once and nothing in the package could
produce one, so `failed` was structurally always zero and `if (!outcome.ok)` was dead code
written against a documented contract.

duck-iam keys an outcome by the `row` itself rather than by an id, because a role assignment
is identified by a `(subject, role, scope)` triple of free-form strings and every encoding of
three of those into one key is ambiguous or unreadable -- an earlier version joined them with
a space, and `('a b', 'c')` collided with `('a', 'b c')`. Outcomes are in input order either
way, so matching by index stays exact.

**duck-auth** offers `softDeleteMany`, `restoreMany`, `eraseMany`, `updateProfileMany`,
`linkMany` and `unlinkMany` on `identities`; `revokeAllForIdentities` and `revokeByHashes`
on `sessions`; and `deleteByIdentities` on the credential store.

**duck-iam** offers `assignRoles`, `revokeRoles`, `moveRoleScopes` and `invalidateSubjects`
on `admin`. Every row is validated before any is written, so a malformed row aborts the
batch instead of half-applying it, and each affected subject is invalidated once however
many rows named it.

Each batch collapses to one statement per table where the adapter can express it and loops
the single-row method otherwise, so every adapter supports every batch form.

<Callout type="warning" title="A looped batch is not atomic on its own">
Only the set-based path is one statement. Where the adapter loops, a row that throws part-way
leaves the rows before it already written. duck-iam settles what it can -- every requested
subject is invalidated, and only rows known to have landed are announced -- but the store has
moved and the batch did not finish.

Running the batch on a transaction you own is what makes it atomic: the throw aborts your
transaction and the landed rows roll back with everything else.
</Callout>

### Applied is not the same as changed

duck-iam's role writes are idempotent, so every row of a grant or revoke is `ok`: granting a
role a subject already holds is success, not a miss, exactly as the single-row `assignRole`
treats it. That makes `applied` a poor signal on its own, so the outcome carries `changed`
as well.

```typescript
const again = await perms.admin.assignRoles([{ subjectId: 'u1', roleId: 'admin' }])
again.applied // 1 - the grant is in place

const [outcome] = again.outcomes
outcome?.value.changed // false - this call is not what put it there
```

| `changed` | Meaning |
|---|---|
| `true` | this row accounts for a write the statement made |
| `false` | the row was already in the requested state, or an earlier row of the batch already accounts for that write |
| absent | the adapter could not say, and did not guess |

Every write is credited to exactly one row -- the first that accounts for it. Listing the
same triple twice reports `true` then `false` rather than both rows claiming a write the
database made once, and revoking `{u1, admin}` alongside `{u1, admin, scope: 'org-1'}`
credits the wildcard row, which already covers the narrower one. Neither batch is rejected;
both are answered honestly.

<Callout type="info">
`changed` is read off a `RETURNING` clause on the write itself, so it costs nothing: the
conflict clause has already skipped the duplicates, and the driver names the rows that
landed on the round trip the write was making anyway.

Where there is no `RETURNING` to read -- MySQL, and every adapter that loops the single-row
methods, which return `void` -- the field is absent rather than guessed. Filling it in would
mean a second round trip for an answer the caller may not want, so those adapters say
nothing instead. Check `'changed' in outcome.value` before relying on it.

An absent `changed` is not "nothing was written". On MySQL the grants land; the driver just
cannot name which of them were new.
</Callout>

### The MySQL upsert is a read-then-write

Postgres and SQLite upsert with a single target-scoped `ON CONFLICT` clause, so the whole
write is one atomic statement and a collision on some *other* unique index throws rather than
overwriting an unrelated row.

MySQL has no `ON CONFLICT`, and its `onDuplicateKeyUpdate` fires on *any* unique-index
violation rather than only the one you named -- which would let a row with a fresh `id`
silently overwrite an unrelated row it collided with. So the MySQL adapter probes by target
first and then issues a plain `UPDATE` or a plain `INSERT`, and a genuine secondary-index
collision surfaces as a thrown duplicate-entry error.

The consequence for a caller is a window between the probe and the write. Two concurrent
`saveRole` calls for the same new id can both see nothing and both insert; the primary key
rejects the loser, loudly, which is the right failure -- but it is a failure a Postgres or
SQLite deployment does not see. Running the write on a transaction narrows the window to your
isolation level rather than closing it.

### Hard and soft failures

A **hard** failure -- a constraint violation, a driver error -- throws in both packages. Inside
your transaction that aborts the whole thing, which is what makes a batch atomic with your own
work: one bad row rolls the entire batch back, including the rows that had already applied.

A **soft** failure -- a lost optimistic-lock race, a row that was not there -- is reported per
row and does not throw. This channel is duck-auth's only: a bulk profile update tells you which
rows lost the version race instead of dying on the first one. duck-iam has no soft-failure
channel, because it has no optimistic-lock race to lose and an idempotent write has no "row that
was not there" -- everything that does not throw is applied.
