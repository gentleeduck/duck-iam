```ts
import { drizzlePgAdapter } from '@gentleduck/auth/adapters/drizzle/pg'
import { valkeyEvents, valkeySessionImpl } from '@gentleduck/auth/adapters/valkey'
import { createAuth } from '@gentleduck/auth/core'
import { valkeyLimiter } from '@gentleduck/auth/limiters/valkey'
import { passwords } from '@gentleduck/auth/providers/passwords'
import Redis from 'ioredis'

const redis = new Redis(process.env.REDIS_URL ?? '')
const sql = drizzlePgAdapter(process.env.DATABASE_URL ?? '')

export const auth = createAuth({
  baseUrl: 'https://app.example.com',
  stores: { identities: sql.identities, credentials: sql.credentials, sessions: valkeySessionImpl({ redis }) },
  limiter: valkeyLimiter({ redis }),
  events: valkeyEvents({ cmd: redis, sub: new Redis(process.env.REDIS_URL ?? '') }),
  providers: [passwords()],
  strict: false,
})

auth.events.on('lockout', (event) => alertOps(event))
auth.strict()
```

Every production check reads `NODE_ENV`. Only `development` and `test` relax them, so an unset or unknown value is production. `createAuth` runs `strict()` as it returns, and production requires a `lockout` listener, which cannot exist before `createAuth` returns, so a production engine passes `strict: false` and calls `auth.strict()` once it is subscribed.

Outside production, `strict()` checks only the [compliance preset](/duck-auth/core/compliance), if one is set. A failure throws one `AUTH_MISCONFIGURED` whose `meta.detail` lists every problem.

## What production refuses

| Area | Refused |
| --- | --- |
| Limiter | None, `NoopLimiter`, or the in-process `MemoryLimiter`. |
| Stores | A memory store in any `stores` slot. |
| Events | No bus, or the in-process one, while it holds a `fleet` handler. |
| Transport | A JWT transport signing HS256 with a key under 32 bytes. A composite's parts are checked one by one. |
| OAuth | A `stateSigningSecret` under 32 bytes. |
| Passkey | The in-process challenge store. |
| Magic link | No `deliver`, so no link could be sent. |
| Passwords | A hasher below its own defaults: scrypt `N` under 2^14, `r` under 8 or `keylen` under 32; Argon2id `memoryCost` under 19456, `timeCost` under 2 or `hashLength` under 32. |
| Engine | A `baseUrl` that is not `https`, no provider, or no `lockout` listener. |

A store, transport, provider or hasher of your own publishes none of the markers these checks read, so it is not judged.

The in-process pieces are refused because a second instance cannot see them: a limiter budget is granted once per instance, and a revocation, OAuth `state` or passkey challenge used on one instance stays live on the others. [Redis and Valkey](/duck-auth/adapters/redis) has the shared versions.

## Refused at construction

These throw `AUTH_MISCONFIGURED` in production as they are built, before `strict()` runs:

- The null captcha verifier, `MemoryDPoPNonceStore`, `MemoryIdempotency`, and the OIDC OP's in-memory stores, which `createOidcOP` falls back to for a store it is not given.
- An OAuth provider with no `nonceStore`, and a SAML provider with no `replayStore`.
- A captcha `endpoint` or webhook `url` over plain http or on loopback. Private, link-local and cloud-metadata hosts are refused in every environment.
- An OIDC issuer over plain http.

Cookies are Secure in production. Outside it they are not, and a `__Host-` or `__Secure-` prefix is dropped from the name along with Secure, so plain-http development works with the defaults: the session cookie is `duck-sid` and its CSRF companion `duck-csrf`. `sameSite: 'none'` keeps a cookie Secure in every environment.

Reporting, scope and a deployment checklist are in [SECURITY.md](https://github.com/gentleeduck/duck-iam/blob/main/packages/duck-auth/SECURITY.md).
